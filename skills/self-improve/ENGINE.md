# Self-Improve — Engine

> Defines trigger rules, execution flow, layer creation rules, and module lifecycle.

---

## Trigger mechanism

### Scheduled trigger (every 3 days by default)

```
Cron:    0 4 */3 * *    (every 3 days at 04:00)
Model:   configurable in user-config.yaml (default: omniroute/T2)
Agent:   <main_agent>   from user-config.yaml
Timezone: <owner.timezone>
```

The Cron message is generated by `scripts/setup.mjs` and written to `proposals/PENDING.md`. Once approved and added to your OpenClaw configuration, it triggers the full pipeline.

### Execution flow

```
0. backup              → snapshot critical files to data/backup/ (pure file op; no git)
1. scan                 → feedback-collector extracts signals from memory logs + last reflections.md
2. distill + classify   → three-level distillation + theme settlement + value-density annotation
3. elevate              → memory-layer manages hot.md (≥3 uses within 7 days → promote)
4. route                → proposer considers holistically; outputs rule / blog / methodology / skill
5. revisit              → deep read of high-value items; deep output (optional)
6. wrap-up              → reflection + profile + notification + checkpoint
```

## Execution principles

1. **Fully automatic processing** — collection through distillation; no human in the loop
2. **Only solidification requires confirmation** — writing to `AGENTS.md` and other system files requires approval
3. **Self-determined format** — the language model decides how to organize language and which section to extend
4. **Can create new** — new themes / projects / directories are created on demand
5. **Index auto-update** — relevant index files are updated after every write
6. **Fault-tolerant continuation** — when a step fails, log the error and continue; final status becomes `partial`

## Module dependency graph

```
feedback-collector (no dependencies)
      │
      ▼
distill-classifier (depends on feedback-collector)
      │
      ▼
memory-layer (no dependencies)
      │
      ├─► knowledge-archiver   (depends on memory-layer)
      ├─► methodology-extractor (depends on memory-layer)
      └─► proposer             (depends on memory-layer)
profiler   (depends on feedback-collector)
reflector  (no dependencies)
notify     (depends on proposer)
```

**Execution order:** topologically sorted. Upstream modules always complete first.

## Module lifecycle

### Enabling / disabling

**Method A — edit `config.yaml`:**

```yaml
modules:
  profiler:
    enabled: false   # set to false to disable
```

**Method B — at runtime** (when implemented in `scripts/module.mjs`):

```bash
node scripts/module.mjs enable  profiler
node scripts/module.mjs disable profiler
```

### Adding a new module

```
1. create directory: modules/<new-module>/
2. write MODULE.md following the standard format
3. register in config.yaml under modules
4. create any new data subdirectory under data/
5. append an entry to changelog.md
```

**Standard `MODULE.md`:**

```markdown
# Module name

> Version: x.y.z
> Status: active | disabled

## Responsibility
One-line description.

## Input
Where to read data from.

## Output
Where to write data to.

## Interface
How to invoke.

## Dependencies
Which modules this depends on.
```

### Removing a module

```
1. set enabled: false in config.yaml
2. confirm no other module depends on it
3. delete modules/<name>/ directory
4. remove registration from config.yaml
5. if data deletion is needed, confirm with user first
6. append to changelog.md
```

> Data files are **not** automatically deleted. Manual confirmation is required.

## Prompt system

All module execution instructions are centrally managed in `prompts/`:

| Prompt | Purpose | When used |
|---|---|---|
| `cron-trigger.md` | Cron entry point | Every scheduled run |
| `feedback-collector.md` | Scan conversations, extract signals | Step 1 |
| `distill-classifier.md` | Three-level distillation + classification + value density | Step 2 |
| `memory-layer.md` | Tiered memory management | Step 3 |
| `proposer.md` | Output routing + solidification proposals | Step 4 |
| `reflector.md` | Self-reflection | Step 5 |
| `profiler.md` | Team capability profile (every 3rd run) | Step 6 |
| `notify.md` | Notify user | Step 7 |
| `execution.md` | Apply after approval | Independent trigger |

> Prompt quality is the core of the system. Test thoroughly before modifying.

## Failure handling

| Failure type | Behavior |
|---|---|
| Missing required file | Log warning; treat module as no-op; continue |
| Invalid YAML | Abort run; print parse error; do not modify state |
| Permission denied | Log; mark step `failed`; continue to next step |
| LLM call failure | Retry once; if still failing, log and skip step |
| Disk full | Abort run; alert user via notification |

The framework **never** silently corrupts state. Every mutation is logged.
